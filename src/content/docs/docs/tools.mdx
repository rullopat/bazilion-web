The tools an Agent can use depend on how its turn starts. Check this before
moving a workflow from local chat to Telegram, a schedule, or remote access.

## Which tools can this turn use?

A **local operator turn** is a direct web or CLI chat while
`BAZILION_PUBLIC_ORIGIN` is unset. It uses your configured tools and shell mode.
A **protected turn** is started by Telegram, a trigger, inbox delivery, or an
approved delivery. Setting `BAZILION_PUBLIC_ORIGIN` also makes HTTP chat use
protected execution, including requests made from the same machine.

On a narrow screen, scroll the table sideways to compare both turn types.

| Capability | Local operator turn | Protected normal turn |
| --- | --- | --- |
| Coding | Pi host tools by default; Docker `bash` when selected | Docker `bash`; no host coding tools |
| Docker required | Only when configured | Always, even if `BAZILION_BASH_SANDBOX=off` |
| Web fetch | Guarded fetch; configured rendering integrations | Uncredentialed, SSRF-guarded fetch |
| Web discovery | Configured backends or eligible native OpenAI/ChatGPT route | Separate opt-in protected SearXNG only; no native search |
| Managed browser / MCP | When enabled/admitted; MCP stdio requires Linux | Unavailable |
| Team memory, mailbox, guarded context, Agent home tools | Available | Available through scoped tools |
| File delivery | Available | Available from the Team workspace |
| Provider credentials | Configured runtime | Only the selected provider's validated credential fields |

Reviewed learning uses a separate restricted review surface; it does not get
the normal Agent toolset. See [Daily operations](/docs/operations/#review-and-apply-a-lesson).

Enabling a browser or MCP server does not add it to protected turns. A failed
protected preflight stops the turn; it never falls back to host execution.

## Prepare Docker for protected work

On the daemon host, install and start a local Docker engine and ensure the user
running Bazilion can access its Unix socket. Prepare the default image yourself:

```sh
docker context show
docker info
docker pull debian:bookworm-slim
docker image inspect debian:bookworm-slim
bazilion doctor
```

Bazilion uses `--pull never`: it will not download a missing image during a
turn. Use `BAZILION_BASH_SANDBOX_IMAGE` in the daemon environment to select a
different locally installed compatible image, then restart. Images with
declared volumes and remote Docker endpoints are rejected. The default image
is minimal; prepare a compatible image with any project tools you need because
shell commands run without network access.

Confirm the protected-work readiness reported by `bazilion doctor`, then test
the intended Agent/provider through its actual Telegram, trigger, or remote
path. General readiness does not prove every provider credential or project
command works. Docker setup is required before those workflows can run.

## The built-in tools

Within the capability limits above, normal turns have:

- **coding tools** — host tools or Docker `bash` for Team project files,
- **web tools** — guarded fetch; ordinary configured/native discovery or separately configured protected SearXNG within their distinct boundaries,
- **mailbox tools** — `send_message`, `read_inbox`, `wait_for_reply`, and
  `approval_status`,
- **memory tools** — search and write the Team's [shared memory](/docs/concepts/#shared-usermd-and-memory),
- **guarded Team context tools** — `user_md_get` and concurrency-checked
  `user_md_write`,
- **home-file tools** — read and update its own `IDENTITY.md` and notes.

Because a Team root can be a symlink to a real project (see
[Core concepts](/docs/concepts/#teams)), Agents work on actual code rather than
a throwaway sandbox.

## Shell isolation and dangerous-command approval

For local operator turns, Pi's host-backed `read`, `bash`, `edit`, `write`, `grep`, `find`,
and `ls` tools operate from the Team root. This is convenient, but the working
directory is not a security boundary.

Set `BAZILION_BASH_SANDBOX=docker` to replace the host-backed coding surface
with a containerized `bash`. Every invocation uses a fresh container with no
network, a read-only root, a temporary `/tmp`, a scrubbed environment, and the
Team workspace as its only writable mount. Team memory, Agent inputs, and
attached skills are mounted read-only. Bazilion accepts only a local Unix-socket
Docker context and a pre-existing compatible image; a missing or invalid setup
fails closed instead of falling back to the host.

`BAZILION_BASH_APPROVAL=dangerous` is a separate control. Commands classified
as dangerous pause for approval inline in web chat or at an interactive CLI
prompt. Decisions are scoped to that turn; cancellation and timeouts clean up
the request, and non-interactive turns deny automatically. This is independent
of durable Team Policy communication approvals.

```sh
BAZILION_BASH_SANDBOX=docker \
BAZILION_BASH_APPROVAL=dangerous \
bazilion dashboard
```

## Web research and optional managed browsing

Ordinary interactive discovery uses **Config → Web Search** and the Agent's **Web discovery**
status. Auto preserves configured Brave, then SearXNG; otherwise eligible OpenAI/ChatGPT Agents
use their own selected model/account. Explicit native routes must match the Agent's provider.
No error or missing entitlement silently switches provider, account, model or browser.

Status is passive, not a provider probe. API-key native search remains experimental/live-unqualified;
the subscription journey has bounded historical acceptance, not general entitlement. Existing model
selections do not change automatically. Provider-hosted search networking is not confined by the
browser proxy. Agents must read original sources through guarded fetch and cite what they read.

Local interactive turns can separately use an enabled **managed browser**, attached through
Playwright. It is accessibility-tree-first: Agents observe current references with their matching
`observationId`, act on those references and never blindly replay uncertain submissions.

The suite covers navigation and interaction — `browser_navigate`,
`browser_snapshot`, `browser_click`, `browser_type`, `browser_fill_form`,
`browser_select`, `browser_hover`, `browser_press_key`, `browser_go_back`,
`browser_tabs`, `browser_take_screenshot`, `browser_console`, and
`browser_network`.

Bazilion launches its installed browser on an Agent's daemon-owned persistent profile and attaches
Playwright; browser state can contain sensitive cookies/logins. Profiles are excluded from backup.
Configuration/session readiness does not prove any site, login or anti-bot access will work.
Protected, scheduled/inbox and restricted turns do not receive browsing capability.

Operator controls (not Agent recovery tools):

```sh
bazilion agent browser status <agent-id>
bazilion agent browser stop <agent-id>
bazilion agent browser reset <agent-id> --yes
```

Stop preserves the profile; reset is destructive. Unknown/live ownership is recovery-required:
never manually delete profile directories, locks or owner markers. Downloads are denied.

<Aside type="caution">
The normal validating **SSRF proxy** blocks loopback/private-network targets, including
persisted service-worker egress. `BROWSER_ALLOW_PRIVATE_NETWORK=true` is a local-development
exception that disables this protection, not an Agent capability or site-access guarantee.
</Aside>

## MCP servers

The daemon is a **Model Context Protocol** client. Connect an MCP server and its
tools are discovered automatically and injected into configured local operator turns,
namespaced as `mcp__<server>__<tool>` so they never collide with built-ins.

The standalone daemon-owned MCP client supports two transports:

- **stdio** — local subprocess execution on **Linux only**, with owned process-tree retirement;
  other platforms refuse before slot allocation/spawn,
- **Streamable HTTP** — a remote server over HTTP, with optional bearer auth.

Legacy **SSE is retired**, not imported or adapted. No automatic OAuth, ambient Pi discovery or
uncertain tool-call replay is added. MCP remains unavailable to protected/restricted turns.

Manage servers from the CLI:

```sh
bazilion mcp add <name> …     # register a server
bazilion mcp list             # list configured servers
bazilion mcp show <name>      # inspect one server and its tools
bazilion mcp test <name>      # connect and verify it responds
bazilion mcp enable <name>
bazilion mcp disable <name>
bazilion mcp rm <name>
```

The same servers are managed visually on the **`/config/mcp`** page.

## File handling

Files move **both ways** between you and your agents, across the web UI,
Telegram, and the CLI.

**Inbound.** Attach a file and the daemon classifies it: images are passed to the
model as vision input, while other files are stored where the agent can open them
with its coding tools. From the CLI:

```sh
bazilion agent chat <agent-id> --message "Describe this screenshot" --image ./screenshot.png
bazilion agent chat <agent-id> --message "Summarize this report" --file ./report.pdf
```

**Outbound.** Agents send files back with the **`deliver_file`** tool (up to
**25 MB** per file). These deliveries arrive as downloadable files, including
Telegram documents. Images returned by tools such as browser screenshots are
displayed separately in web chat and sent as Telegram photos when supported.

<Aside type="note">
Audio and video files are stored as attachments; they are not native audio/video
model input. Browser and MCP availability follows the turn boundary above,
regardless of which client displays the conversation.
</Aside>

## Durable files and live clarification in 0.15.0

`deliver_file` captures an immutable Team-owned result, rather than relying on transient stream
bytes. Saved chat cards and the Team Results library survive reload and restart; downloads retain
the original filename. See [Saved results](/docs/results/) for authorization, previews and limits.

`ask_user` is available only on eligible live human routes. It offers bounded choices, Other or
Skip and waits for a correlated answer in the originating conversation. Scheduled, inbox and review
turns do not inherit this capability. See [Agent questions](/docs/questions/).
